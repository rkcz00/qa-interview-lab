# QA Interview Lab

QA Interview Lab — учебное веб-приложение для подготовки Middle/Senior QA Engineers к техническим собеседованиям на русском и английском языках.

Вторая цель проекта — портфолио с проверяемыми примерами работы с Codex, Python, React, PostgreSQL, Pytest, Playwright, Docker и GitLab CI.

## Текущий статус

QIL-003 / Этап A: создан минимальный каркас Django/DRF и React/TypeScript/Vite, custom User и начальная миграция, Compose-конфигурация PostgreSQL и локальные настройки. Git-репозитория и CI pipeline пока нет.

В этапе A проверены Django checks, пять Unit-тестов User без DB, согласованность файлов моделей/миграций, HTTP-ответ backend через WSGI без базы, HTTP-ответ Vite, TypeScript и production build. Каркас не является готовым MVP.

QIL-003 / Этап B: ручной прогон пользователем в обычном PowerShell подтверждён переданным выводом: Compose, миграции, полный Pytest (7 тестов и 5 подтестов), HTTP 200 и `pip check` успешны; PostgreSQL оставлен healthy. Docker CLI 29.9.2 и Compose 5.6.1 найдены по стандартному пути пользовательской установки, context — `desktop-linux`. В Codex Docker API ранее вернул `permission denied` для `dockerDesktopLinuxEngine`: `DOCKER_API_BLOCKED`. Ограничение не обходилось.

QIL-003 / Этап C: пользователь сохранил действующие секреты через `save-local-env.py` в локальный `.env`, без ротации пароля PostgreSQL. Проверены обязательные ключи, несекретные значения шаблона, загрузка настроек Django из файла, Django checks и `pip check`. В этом этапе Docker не вызывался.

Описанные ниже функции являются требованиями к будущему приложению. Наличие документации не означает, что функции уже реализованы или протестированы.

## Возможности MVP

- Регистрация и вход по уникальному email и паролю; Django sessions и CSRF-защита.
- Каталог опубликованных тем, статья и словарь терминов для каждой темы.
- Независимый выбор русского или английского языка статьи и тестирования.
- Вопросы Single-choice и Multiple-choice с проверкой на backend.
- Результат теста, повторные попытки и сохранённая история пользователя.
- Отметка статьи кнопкой «Прочитано» и сохранение прогресса между входами.
- Управление контентом и публикацией через Django Admin.

## Ключевые правила

- Multiple-choice засчитывается только при выборе полного и точного набора правильных вариантов; частичных баллов нет.
- До отправки попытки пользовательский API не раскрывает правильные ответы. После отправки результат доступен только владельцу попытки.
- Тема освоена, если статья отмечена прочитанной и есть хотя бы одна завершённая попытка с результатом не ниже 80%.
- Порог проверяется по точному отношению числа верных ответов к числу вопросов, до округления процента для отображения.
- Прогресс общий для обоих языков. Переключение языка не меняет идентификаторы вопросов и вариантов, результаты или отметку «Прочитано».
- Изучение словаря не влияет на освоение темы.
- Для публикации обязательны полноценные русская и английская версии статьи, вопросов, вариантов ответа и словаря. Неполная тема остаётся в Draft.
- Пароли хешируются штатными средствами Django. Пользовательский API не предоставляет доступ к чужому прогрессу и попыткам.

## Технологический стек

| Область | Решение |
| --- | --- |
| Frontend | React + TypeScript + Vite |
| Backend | Python + Django + Django REST Framework |
| База данных | PostgreSQL |
| Управление контентом | Django Admin |
| API-тесты | Python + Pytest + HTTPX |
| E2E-тесты | Playwright + Python + Pytest |
| Локальная инфраструктура | Docker + Docker Compose |
| CI/CD | GitLab CI |

Архитектура — модульный монолит в одном репозитории: один Django backend с внутренними модулями, один React frontend и одна PostgreSQL.

Каркас использует Python 3.14.2, Django 5.2.19 LTS, DRF 3.18.3, psycopg 3.3.8; Node.js 24.22.2, npm.cmd 11.19.1, React 19.3.1, TypeScript 7.0.2, Vite 8.3.6. В Compose выбран официальный образ `postgres:17.11`; запуск подтверждён ручным прогоном этапа B. Выбор Django LTS и поддержки Python проверен по [документации Django](https://docs.djangoproject.com/en/5.2/releases/5.2/) и [требованиям DRF](https://www.django-rest-framework.org/). Frontend основан на [официальном React/TypeScript-шаблоне Vite](https://github.com/vitejs/vite/tree/main/packages/create-vite/template-react-ts).

Прямые зависимости backend перечислены в `backend/requirements.txt`, разрешённые версии — в `backend/requirements.lock`. Зависимости frontend фиксируются в `frontend/package.json` и `frontend/package-lock.json`. Python-пакеты находятся только в `.venv`, Node-пакеты — только во `frontend/node_modules`. `psycopg[binary]` позволяет подключаться к PostgreSQL без установки компилятора и системного клиента PostgreSQL.

QA-зависимости: Pytest 9.1.1 и pytest-django 4.14.0. `backend/requirements-dev.txt` добавляет их поверх locked runtime, а `backend/requirements-dev.lock` фиксирует полное окружение разработки. Runtime lock-файл сохранён без изменений; глобальные пакеты не устанавливались.

## Как начать работу с Codex

1. Прочитайте PRD и открытые вопросы в конце документа.
2. Выберите одну задачу из backlog и явно задайте её границы. Для последующих интеграционных прогонов PostgreSQL нужен доступный Docker API; ручной прогон этапа B уже подтверждён.
3. Попросите Codex показать план, границы задачи и проверки результата.
4. Отдельно согласуйте необходимые установки и изменения окружения. Разрешение на документацию их не включает.
5. После выполнения изучите отчёт и результаты проверок. Следующая задача начинается только по вашему указанию.

Пример запроса: «Начни только анализ QIL-002. Проверь доступные инструменты, предложи версии и объясни зависимости. Ничего не устанавливай».

## Локальное окружение и команды

Все команды ниже выполняются из корня проекта, кроме блоков с явным `Set-Location`. В Windows используйте `npm.cmd`, чтобы не менять ExecutionPolicy из-за `npm.ps1`. Активация `.venv` не нужна: Python вызывается по пути к проектному окружению.

### Зависимости

В текущей рабочей папке `.venv` и `frontend/node_modules` уже созданы. При повторной подготовке окружения сначала убедитесь, что `python --version` показывает выбранную ветку Python 3.14. Если команда ведёт на WindowsApps alias, используйте полный путь к уже установленному Python; PATH и aliases автоматически не меняйте.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend\requirements-dev.lock
Set-Location frontend
npm.cmd ci
Set-Location ..
```

Стандартная команда `python -m venv` через alias в среде Codex не проверена: при создании окружения использован фактический путь к Python 3.14.2. На первом запуске `ensurepip` получил отказ в доступе к TEMP sandbox; подготовка завершена с временным каталогом внутри `.cache`, без изменения системных переменных. Команды повторной установки приведены для воспроизведения, а не как отдельный выполненный clean-install тест.

### Локальные секреты

В текущей рабочей папке `.env` уже создан пользователем в этапе C. Он содержит настройки из `.env.example` и секреты, перенесённые из PowerShell успешного интеграционного прогона. Повторно генерировать пароль существующей PostgreSQL не нужно: новое значение в файле не меняет пароль уже инициализированной базы.

Для сохранения действующих переменных из прежнего PowerShell используется файл ниже. Если `.env` существует, он только проверяет обязательные ключи и не перезаписывает файл. Если пароль отсутствует в процессе, создание останавливается; новый пароль PostgreSQL автоматически не генерируется.

```powershell
.\.venv\Scripts\python.exe .\save-local-env.py
```

Установленный Python 3.14.2 не поддерживает ранее ошибочно указанный `--env-file`. Django получает настройки из переменных процесса; `.env` автоматически читает Compose, но не текущие настройки Django. Дополнительный dotenv-пакет не устанавливался. Vite не получает секреты backend. Не публикуйте заполненный `.env` или раскрытую Compose-конфигурацию.

### Загрузка настроек в новый PowerShell

Один раз в каждом новом окне, из корня проекта, загрузите простой формат `KEY=value`, создаваемый `save-local-env.py`. Этот блок не печатает значения и устанавливает только переменные проекта в текущем процессе, без изменения PATH или системных настроек:

```powershell
Get-Content -LiteralPath '.env' -Encoding UTF8 | ForEach-Object {
    if ($_ -match '^(DJANGO_[A-Z0-9_]+|POSTGRES_[A-Z0-9_]+)=(.*)$') {
        [System.Environment]::SetEnvironmentVariable($Matches[1], $Matches[2], 'Process')
    }
}
```

### Доступные проверки

После загрузки `.env` в текущий PowerShell:

```powershell
.\.venv\Scripts\python.exe backend\manage.py check
.\.venv\Scripts\python.exe backend\manage.py test apps.accounts.tests.test_user
.\.venv\Scripts\python.exe backend\manage.py makemigrations --check --dry-run
Set-Location frontend
npm.cmd run build
npm.cmd run dev
```

Первые проверки и сборка выполнены в этапе A с временными значениями секретов в памяти. В ручном этапе B проверены PostgreSQL, миграции и полный набор тестов; в этапе C Django checks проверены с загрузкой сохранённого `.env`. Пять Unit-тестов не обращаются к DB; сохранение User в них подменено. Они прошли и через runner Django, и через Pytest с плагином Django. Отдельный HTTPX harness ещё не создан. Frontend открывается на `http://127.0.0.1:5173`; `Ctrl+C` останавливает dev server. HTTP-проверка подтвердила выдачу страницы и преобразованного React-модуля, браузерный рендер не проверялся.

После загрузки локального `.env` Unit-тесты через Pytest запускаются так; отдельный pytest-конфиг для этого не нужен:

```powershell
Set-Location backend
..\.venv\Scripts\python.exe -m pytest apps/accounts/tests/test_user.py --ds=config.settings -q
Set-Location ..
```

Для полного прогона после готовности PostgreSQL замените `apps/accounts/tests/test_user.py` на `apps/accounts/tests`. Ручной прогон этапа B подтвердил 7 успешных тестов и 5 подтестов, включая 2 DB-теста; в этапе C он не повторялся.

### Запуск с PostgreSQL — в среде с доступом к Docker API

Docker Desktop уже подтверждён пользователем; его переустановка не требуется. Следующие команды выполняются из среды с доступом к Docker API после загрузки `.env`; в Codex запуск контейнера заблокирован. Обычный `docker compose config` раскрывает подставленные значения: для валидации используйте `--quiet`, не публикуйте секреты.

```powershell
docker compose config --quiet
docker compose up -d --wait postgres
.\.venv\Scripts\python.exe backend\manage.py migrate
.\.venv\Scripts\python.exe backend\manage.py runserver 127.0.0.1:8000
```

Корень backend возвращает статическую строку `QA Interview Lab backend`, без DB и пользовательских данных. Обычный `runserver` сначала проверяет миграции и требует доступной PostgreSQL. Успешный HTTP smoke через WSGI без DB не означает успешного запуска полной связки.

После готовности PostgreSQL выполните в другом терминале интеграционные проверки, предварительно загрузив в нём `.env`:

```powershell
.\.venv\Scripts\python.exe backend\manage.py test apps.accounts.tests.test_user_database
```

Они создают отдельную тестовую базу `POSTGRES_TEST_DB`, проверяют login и DB-уникальность при обходе `save()`. Имя тестовой базы не должно совпадать с базой разработки. Эти проверки и применение миграции подтверждены ручным прогоном этапа B. SQLite не используется. Volume PostgreSQL сохраняется; его удаление в инструкции не включено.

### Что уже заложено в backend

- `AUTH_USER_MODEL = accounts.User` задан до начальной миграции; `USERNAME_FIELD = email`, поля username нет.
- Email обрезается по краям и приводится к нижнему регистру; точки и `+suffix` сохраняются. В миграции есть обычная уникальность email и функциональное ограничение `Lower(Trim(email))`.
- Пароли обрабатываются штатными средствами Django. DRF использует только SessionAuthentication и требует входа по умолчанию; middleware CSRF подключён.
- Session cookie — HttpOnly/SameSite=Lax, срок 14 дней. Secure для session/CSRF включён при `DJANGO_DEBUG=false`; локальный HTTP использует `DJANGO_DEBUG=true`. Это локальные настройки, не принятая конфигурация публичного deploy.
- Технический Django Admin доступен по `/admin/` после применения миграций. Штатная команда `createsuperuser` создаёт администратора с email для входа.
- Vite проксирует `/api` на backend с сохранением Host/Origin. Learner API, анонимные CSRF/register/login endpoints, snapshots, ownership и Content Admin запланированы.

## Что находится за пределами MVP

Практические задания, открытые вопросы, повторение сложных тем, подтверждение email и восстановление пароля. Для них нет задач реализации в текущем MVP backlog.

Публичный хостинг и автоматический deploy пока не выбраны. GitLab CI в MVP обеспечивает сборку и проверки; стратегия развёртывания согласуется отдельно.

## Ограничения и решения перед разработкой

Нужно выбрать версии инструментов, GitLab Runner и начальные учебные материалы. Язык интерфейса отдельно не согласован: рабочее предположение — русский интерфейс с независимыми переключателями языка статьи и тестирования. Полный перечень вопросов находится в PRD.

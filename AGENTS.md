# Правила работы Codex в QA Interview Lab

Эти правила действуют для всего проекта. Явные указания пользователя определяют разрешённый объём текущей задачи. При неясном конфликте нужно объяснить его и уточнить решение до зависимых изменений.

## Контекст пользователя и проекта

Пользователь — Senior QA Engineer, создающий своё первое полноценное веб-приложение с Codex. Сохранять инженерные требования к качеству, но объяснять незнакомые frontend/backend-инструменты и решения простым языком.

Цель — обучение и работающий QA Interview Lab. Документация ведётся на русском языке; названия технологий, сущностей и стандартные технические термины можно оставлять на английском.

## Одна задача за раз

- Выполнять только одну согласованную задачу с конкретным идентификатором и границами.
- Перед существенными изменениями показывать краткий план: что изменится, почему и как будет проверено.
- Если пользователь установил этап подтверждения, остановиться на нём и дождаться явного ответа.
- Согласованный план выполнять в пределах задачи; не запрашивать повторно уже полученное разрешение на те же действия.
- Не переходить автоматически к следующей задаче, даже если она очевидна или мала.
- Не добавлять функции, рефакторинг или инфраструктуру вне согласованного объёма. Новые предложения записывать в отчёт для обсуждения.

## Перед изменениями

1. Проверить рабочую папку, актуальные инструкции и существующие файлы.
2. Прочитать относящиеся к задаче требования и архитектурные решения.
3. Если есть Git-репозиторий, выполнить доступные проверки состояния без изменения файлов. Существующие пользовательские изменения сохранить.
4. Назвать критерии приёмки и существенные неизвестные. Не выдавать предположение за согласованное требование.
5. Использовать доступные релевантные skills как инструкции. Наличие skill не означает запуск отдельного агента или наличие его внешних инструментов.

## Разрешения и ограничения

- Не выполнять Git commit или push без явного разрешения пользователя на соответствующее действие. Разрешение на commit не подразумевает разрешения на push.
- Не инициализировать Git-репозиторий, не менять remote и не создавать внешние проекты без согласования соответствующей задачи.
- Не устанавливать и не обновлять зависимости, инструменты, браузерные бинарные файлы Playwright, плагины или skills без согласования. Перед установкой объяснить назначение, версию и место установки.
- Не изменять системное окружение, глобальные настройки, службы, PATH или Docker Desktop без согласования.
- Не запускать субагентов без отдельного явного разрешения. Одобрение обычной задачи или использование skill такого разрешения не даёт.
- Не удалять пользовательские данные, Docker volumes и не выполнять необратимые Git-операции без отдельного согласования точных целей.
- Не публиковать приложение, исходный код или данные во внешних сервисах без разрешения.
- Не выводить секреты, пароли, session cookies и CSRF-токены в отчёты. Не сохранять реальные учётные данные в репозитории и тестовых артефактах.

## Архитектурные правила

- Сохранять согласованный стек: React + TypeScript + Vite; Python + Django + DRF; PostgreSQL; Django Admin; Pytest + HTTPX; Playwright + Python + Pytest; Docker Compose; GitHub Actions.
- Развивать модульный монолит в одном репозитории. Добавление сервиса, библиотеки или отдельного хранилища требует объяснения конкретной необходимости.
- Не добавлять зависимости только ради удобства генерации кода. Сначала проверять возможности согласованных инструментов.
- Объяснять новое решение: какую задачу оно решает, почему подходит проекту, какие имеет ограничения и чем проверяется.
- Пароли обрабатывать штатными средствами Django; использовать Django sessions и CSRF-защиту.
- Проверять права на backend, включая списки и доступ по идентификатору. Владельца прогресса и попытки определять по текущему пользователю.
- Learner API (пользовательский REST API) никогда не возвращает правильные ответы и внутренний snapshot — ни до, ни после submit. Результат после submit содержит только `correct_count`, `total_count`, `percentage`; метаданные истории передаются отдельно от результата.
- Повтор submit с тем же `attempt_id` и тем же нормализованным payload идемпотентен. Изменённый payload завершённой попытки отклоняется с `409 Conflict`, без перезаписи результата и дубликата истории.
- Для Draft запрещены новые попытки и пользовательское чтение статьи/словаря. Снятие публикации не пересчитывает историю, прогресс или освоение; уже начатая попытка может завершиться по своему snapshot.
- Content Admin — отдельная Django-группа с permissions только на контентные модели и их переводы. Прав на `User`, `Attempt`, `TopicProgress` у группы нет; superuser не заменяет эту роль при реализации или проверках.
- Минимальный API-контракт брать из [архитектуры](docs/ARCHITECTURE.md), обязательные CI jobs — из [QA-стратегии](docs/QA_STRATEGY.md). Не ослаблять эти контракты без согласования.
- Сохранять независимость языков статьи и тестирования, стабильность идентификаторов и общий пользовательский прогресс.
- Правила оценивания и освоения брать из PRD. Не менять их ради удобства реализации тестов.

## Проверки результата

- Запускать доступные релевантные проверки в пределах разрешённой задачи. Наличие инструмента не заменяет согласование его установки.
- Для изменения документации проверять наличие файлов, Markdown-структуру, ссылки и согласованность требований.
- Для изменения приложения выбирать необходимые unit, integration, API или E2E-проверки по риску. Не подменять PostgreSQL SQLite в проверках поведения базы.
- Не считать UI-ограничение доказательством серверной безопасности. Проверять доступ второго пользователя напрямую через API.
- Не заявлять об успешном запуске, зелёном CI или работающем deploy без фактических результатов.
- Отмечать фактические статусы: `PASS`, `FAIL`, `NOT_RUN` или `BLOCKED`. Для непройденной проверки указывать причину и влияние.
- Не скрывать ошибки, упавшие проверки и непроверенные предположения. Не отключать проверку и не ослаблять критерии ради зелёного результата.
- Если необходимая проверка требует нового разрешения, выполнить остальные доступные проверки и объяснить, что осталось непроверенным.

## Документация и небольшой размер изменений

- PRD — источник требований; архитектура — источник технических решений. QA-стратегия и backlog должны им соответствовать.
- Изменяя согласованное поведение, синхронизировать связанные документы в пределах разрешённой задачи.
- Статус «запланировано» не заменять на «реализовано» до появления результата и проверок.
- Не создавать Django/React-каркас, тестовые проекты или конфигурацию инфраструктуры в задаче, разрешающей только документацию.
- Хранить изменения небольшими и понятными для проверки пользователем.

## Завершение задачи

Отчёт должен содержать:

1. Что сделано и какие файлы изменены.
2. Почему выбраны эти решения и какие новые понятия стоит изучить.
3. Что реально проверено, с результатами и ограничениями.
4. Что пользователь может проверить самостоятельно.
5. Ошибки, риски, открытые вопросы и одну рекомендуемую следующую задачу.

После каждой завершённой задачи обязательно добавлять раздел «ОТЧЁТ ДЛЯ CHATGPT», независимо от отдельного запроса пользователя. Подробный технический отчёт по пунктам выше сохраняется; краткий блок его не заменяет.

Краткий отчёт оформлять одним Markdown code block, примерно до 1500 символов. Он должен быть самодостаточным и содержать:

- ID задачи и итоговый статус.
- Созданные и изменённые файлы; если таких нет, явно указать это.
- Выполненные действия.
- Результаты реальных проверок; для невыполненных проверок — статус и причину.
- Проблемы и ограничения.
- Один рекомендуемый следующий шаг.

Не включать в краткий блок секреты, токены, персональные данные или большие фрагменты кода. После отчёта остановиться и ждать следующего указания.

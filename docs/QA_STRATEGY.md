# QA-стратегия QA Interview Lab

Статус: план проверок MVP, подготовленный в QIL-001. Тестов приложения пока нет; их выполнение — `NOT_RUN`. Проверка самих документов является отдельной проверкой QIL-001.

Основание: [PRD](PRD.md), [архитектура](ARCHITECTURE.md), [backlog](BACKLOG.md).

## 1. Цели и приоритеты

Проверить основной сценарий подготовки к интервью и наиболее опасные ошибки: доступ к чужим данным, утечку ключей ответов, неверное оценивание, потерю прогресса и рассогласование переводов.

Тесты добавляются вместе с соответствующей функцией, а не отдельной большой задачей после разработки. E2E дополняют более быстрые unit/integration/API-проверки и не заменяют их.

| Приоритет | Риск | Что служит доказательством |
| --- | --- | --- |
| P0 | Пароль или данные одного пользователя доступны другому | DB-проверка хеша, HTTP-проверки двух пользователей и всех защищённых действий |
| P0 | Learner API раскрывает правильные ответы или внутренний snapshot до/после submit | Проверка разрешённых схем payload, вложенных структур, истории и ошибок API |
| P0 | Multiple-choice или порог 80% считаются неверно | Таблицы решений и граничные unit/API-тесты |
| P1 | Результаты теряются, дублируются или меняются после редактирования | Новый вход, повтор отправки, конкурентная отправка, тест снимка |
| P1 | Язык влияет на ID, ответы или прогресс | Все четыре комбинации языков и переключение внутри попытки |
| P1 | Неполная тема опубликована или снятие публикации нарушает доступ/прогресс | Негативные проверки публикации, запрет новых попыток/чтения Draft и сохранность истории/освоения |

## 2. Уровни тестирования

| Уровень | Инструменты и окружение | Что проверяем |
| --- | --- | --- |
| Unit | Python + Pytest, без сети и DB | Single-choice/Multiple-choice, нормализацию наборов, пропуски, порог освоения |
| Integration | Pytest + Django и отдельная PostgreSQL | Уникальность email/переводов/прогресса, транзакции, snapshots, публикацию и выборки владельца |
| API | Pytest + HTTPX, реально поднятый Django и отдельная PostgreSQL | HTTP-статусы, схемы, cookies/CSRF, права, языки, историю и идемпотентность |
| E2E | Playwright + Python + Pytest, реальный frontend/backend/PostgreSQL | Критический пользовательский путь, переключатели, формы, сохранение результата |
| Ручная проверка | Браузер и Django Admin | Полноценность переводов, учебную точность, удобство и администрирование |
| Сборка/конфигурация | Django checks, TypeScript/Vite build, GitHub Actions | Совместимость каркасов, настройки и обязательные jobs |

Возможности для lifecycle Django test DB и интеграции Playwright с Pytest согласуются как служебные зависимости в QIL-002. Их наличие сейчас не предполагается. Отдельный JS-тестовый framework на этапе документации не добавляется.

## 4. Оракулы оценивания

### 4.1. Выбор вариантов

| Тип / ключ | Пользователь выбрал | Ожидание |
| --- | --- | --- |
| Single-choice, `{A}` | `{A}` | Один балл |
| Single-choice, `{A}` | `{B}` или пусто | Ноль |
| Single-choice, `{A}` | `{A, B}` | Невалидный запрос, без результата |
| Multiple-choice, `{A, C}` | `{A, C}` или `{C, A}` | Один балл |
| Multiple-choice, `{A, C}` | `{A}` | Ноль |
| Multiple-choice, `{A, C}` | `{A, B, C}` | Ноль |
| Multiple-choice, `{A, C}` | `{B}` или пусто | Ноль |
| Любой тип | Неизвестный ID, повтор ID или вариант другого вопроса | Невалидный запрос, без результата |

Генерация ожидаемых баллов в тестах не должна вызывать ту же функцию, которую тестируем. Для этих наборов ожидания задаются независимо, явно.

### 4.2. Освоение

При наличии отметки «Прочитано» проверяем 79/100 — false, 80/100 — true, 81/100 — true. Без отметки все три случая дают false. Дополнительно: 4/5 — true, 3/5 — false, а 199/250 (79,6%) — false, даже если UI округляет процент до целого.

Проверяем `total_count = 0` как невалидное состояние теста. Нельзя допустить деления на ноль или трактовать пустой тест как успешный. При двух неуспешных попытках баллы не объединяются; проверяется успех хотя бы одной самостоятельной попытки.

Порядок действий также параметризуется: сначала тест, потом «Прочитано» и наоборот. Словарь не участвует ни в одном условии.

### 4.3. Auth UI — QIL-018

Frontend unit-тесты проверяют политику регистрации, отсутствие этих ограничений при login, фиксированные маршруты, безопасные русские сообщения и запоздалые ответы восстановления сессии. Публичный словарь распространённых паролей и Unicode-правила сверяются с locked Django/Python командой `python frontend/tools/check_password_policy.py`; 218 примеров проверяются без обращения к DB. Backend остаётся окончательным валидатором.

Playwright запускает production-сборку через Vite preview и реальный Django с отдельной случайной PostgreSQL-базой. Проверяются прямые маршруты, регистрация без auto-login, вход, восстановление после reload, выход/просроченная сессия, duplicate email, already_authenticated, CSRF-отказ, двойной submit, loading/disabled, timeout/network error, неизвестное состояние при сбое `auth/me/`, клавиатура и мобильная ширина. Успешные запросы и серверные отказы проходят настоящий API; только сетевые сбои/потеря CSRF управляются прерыванием запроса. Пароль и cookies не должны попадать в UI/console/Web Storage.

Fixtures закрывают browser contexts, завершают собственные Django/Vite-процессы и удаляют только свою тестовую базу даже при падении. Исходный `test_frontend_smoke.py` сохранён без изменений и работает без DB/backend. Auth E2E не создаёт trace/HAR/video/auth state с секретами. Это покрытие Auth; Learning добавлен отдельно в QIL-019, приёмка всего MVP ещё предстоит.

### 4.4. Learning UI — QIL-019

Unit-тесты покрывают маршруты, RU по умолчанию, язык материала, безопасные цели после login, порядок API, пустой каталог, 403/404/сетевые ошибки, запоздалые ответы и неизвестную отметку при сбое GET. Только явное действие пользователя вызывает `read`; двойной POST блокируется. Потеря ответа требует подтверждающего GET, без автоматического повторения записи.

Playwright использует реальную SPA/Django/изолированную PostgreSQL. `learning_data.py` ограничен случайной базой прогона; создаёт полный RU/EN-контент через существующие модели и test factory. Fixture разрешает менять/удалять только созданные им topic IDs. Проверяются Published/Draft/missing, порядок, статья/словарь RU/EN, reload/Back/Forward, login с возвратом в Learning, CSRF и отметка только кнопкой, общий прогресс RU/EN, отдельное состояние второго пользователя, снятие публикации перед POST, клавиатура и узкий viewport. HTML/JavaScript статьи выводится текстом. Сетевой сбой управляемо прерывается; серверные отказы и данные проходят настоящий API. Quiz/attempts/scoring UI не входят в эту задачу.

## 5. Тестовые данные и изоляция

- Пользователи A и B, отдельный Content Admin в одноимённой Django-группе без superuser и отдельный технический superuser; только синтетические email/пароли. Последний не используется вместо Content Admin в проверках permissions.
- Полная Published-тема с русской и английской статьёй, словарём и пятью вопросами: три Single-choice, два Multiple-choice. Это тестовая фикстура, а не требование к размеру каждого учебного теста.
- Отдельная Draft-тема, у которой по одному удаляются обязательные переводы и поля.
- Независимые выборки для 79/80/81% в unit/API-проверках; не нужно раздувать каждый браузерный тест сотней вопросов.
- Предсказуемые ID и тексты внутри фикстур; переводы соответствуют одним логическим вопросам/вариантам.
- Раздельные cookies и browser contexts для A, B, Content Admin и технического superuser.

Для DB-тестов используется отдельная PostgreSQL/test DB. Для HTTPX нужен отдельный серверный процесс, использующий именно эту тестовую базу: транзакция тестового процесса сама по себе не изолирует записи другого процесса. Согласовать подготовку и очистку фикстур, завершение сервера и защиту от подключения к базе разработки.

API/E2E не очищают пользовательский Docker volume и не используют производственные учётные данные. Параллельный запуск допускается только после изоляции данных каждого worker; на старте последовательный запуск достаточен.

## 6. Особенности API-проверок

HTTPX работает с реально поднятым Django по HTTP. Проверка через mock transport не считается проверкой реального HTTP-контракта. Клиент сохраняет session/CSRF cookies и после login обновляет CSRF-токен.

Нужно проверять не только статус, но и тело ответа и отсутствие нежелательных изменений базы. Ожидаемые ошибки согласованы с архитектурой: `400` для невалидных данных, `403` для CSRF/неаутентифицированного доступа с SessionAuthentication, `404` для чужой попытки/Draft, `409` для изменённого payload завершённой попытки.

Проверки отсутствия утечки до и после submit опираются на формы данных раздела 9 архитектуры и смысл данных. Одного поиска `is_correct` недостаточно: ключ может попасть в JSON под другим именем, вложенным списком или ошибкой. Result имеет ровно `correct_count`, `total_count`, `percentage`; метаданные истории проверяются отдельно. Поля вопросов допустимы только до submit; внутренний snapshot и ответы пользователя не возвращаются никогда. Bootstrap CSRF и Set-Cookie используются только по назначению и не считаются утечкой.

Для идемпотентности сравниваются ID, payload, результат, `submitted_at` и количество записей до/после повтора. Идентичный нормализованный payload даёт 200, изменённый набор ответов или язык — 409 с кодом `attempt_already_submitted`; проверки порядка ID и пустых ответов соответствуют нормализации в разделе 8.1 архитектуры. При конкуренции одинаковых отправок обе возвращают один результат; при разных payload только одна фиксируется, вторая получает 409. Невалидный payload даёт 400; проверка владельца всегда выполняется раньше выдачи сохранённого результата.

## 7. E2E и ручная приёмка

Основной E2E: регистрация → вход → тема → статья → «Прочитано» → выбор языка теста → оба типа вопросов → отправка → результат → выход → повторный вход → сохранённый прогресс/история.

Четыре комбинации языков проверяются параметризованно; смена языка внутри попытки проверяется отдельно. Дополнительные обязательные сценарии: неуспешный тест, успешная повторная попытка, просмотр словаря без изменения прогресса и отсутствие доступа B к данным A. Для снятой с публикации темы проверяются запрет чтения/новых попыток, сохранение истории/освоения и завершение ранее начатой попытки по snapshot.

Первый обязательный браузер — Chromium. Проверки Firefox/WebKit не считаются выполненными без запуска; расширение матрицы обсуждается по найденным рискам. Проверить основной интерфейс на desktop и узком viewport, клавиатурную навигацию, подписи полей, состояния загрузки и ошибки.

В критических E2E не подменять ответы backend заготовками. Для узкого сценария сетевого сбоя допустимо управляемое прерывание запроса, но оно не заменяет тесты реальной серверной идемпотентности.

Content Admin без superuser вручную оценивает смысл и полноту русских/английских материалов и управляет публикацией. Автоматическая проверка непустого поля не доказывает корректный перевод или учебную точность. Отдельно проверяются запреты административного доступа к User, Attempt и TopicProgress.

## 8. GitHub Actions и диагностические артефакты

Для приёмки MVP обязательны четыре именованных job из [workflow CI](../.github/workflows/ci.yml).

| Job | Минимальные обязательные проверки | Критерий успеха |
| --- | --- | --- |
| `backend_api` | Django checks и согласованность миграций; unit/integration и Pytest + HTTPX API на отдельной PostgreSQL с реальным backend. Покрываются ownership, разрешённые схемы до/после submit, 409/idempotency, Draft и Content Admin | Все проверки выполнены и успешны; API и DB-поведение не подменены mocks/SQLite |
| `frontend_unit` | Node.js согласованной версии, `npm ci` и `npm test` из `frontend`; unit-тесты API-клиента, Auth-валидации, маршрутов и состояния сессии | Все unit-тесты успешны; ненулевой exit code делает job и workflow неуспешными |
| `frontend_check_build` | TypeScript type-check и production build Vite | И проверка типов, и сборка успешны; один build без проверки типов недостаточен |
| `playwright_e2e` | Playwright + Python + Pytest, Chromium, реальный frontend/backend/PostgreSQL; основной путь, четыре пары языков, сохранённый прогресс и изоляция пользователей | Обязательные E2E выполнены и успешны; критический путь не использует mock API |

QIL-019 добавляет Learning и чтение в существующий сбор всей папки `tests/e2e`, без изменения workflow. QIL-022/QIL-023 сохраняют ответственность за полную E2E-приёмку MVP, включая Assessment/Progress. Все четыре job запускаются на push и pull request в `main`. Отсутствующий, skipped, BLOCKED или NOT_RUN job не считается PASS; `continue-on-error` и условных пропусков нет. QIL-018/C подтверждён [run #43175377203](https://github.com/rkcz00/qa-interview-lab/actions/runs/43175377203); GitHub Actions QIL-019 — `NOT_RUN` до отдельно разрешённого push. Локальный PASS не заменяет CI.

Workflow также поддерживает ручной запуск. Jobs выполняются на GitHub-hosted Ubuntu с правом `contents: read`. Backend и Auth E2E используют раздельные PostgreSQL service containers с временными настройками. Успешный локальный прогон подтверждает проверки в локальной среде. Результат GitHub Actions подтверждается фактическим запуском на GitHub.

GitHub Actions хранит JUnit XML backend-прогона и JUnit XML браузерного smoke при падении теста семь дней. Для продуктовых E2E на сбое сохраняется разрешённая диагностика: скриншот и trace только после удаления секретов. Cookies, auth state, session/CSRF-токены, включая тестовые, не публикуются как артефакты; синтетический аккаунт сам по себе не делает сырой trace безопасным. Если безопасный trace получить нельзя, он не публикуется, ограничение явно указывается и сохраняется очищенная диагностика.

Ошибка обязательного теста должна давать ненулевой exit code и неуспешный job. Публикация JUnit сама по себе не меняет статус job. Автоматические повторы не должны скрывать первоначальное падение; flaky-тест разбирается, а не отключается без объяснения.

## 9. Definition of Done задачи

- Выполнены критерии приёмки конкретной задачи и относящиеся требования PRD.
- Добавлены или обновлены необходимые положительные, негативные и регрессионные проверки по риску.
- Релевантные доступные проверки фактически выполнены; причины `NOT_RUN`/`BLOCKED` указаны.
- Нет известных дефектов, нарушающих безопасность, оценивание или сохранность пользовательских данных.
- Документация отражает фактическое состояние; невыполненные проверки не названы успешными.
- Отчёт содержит результат и ограничения; перехода к следующей задаче без указания пользователя нет.

## 10. Приёмка MVP

Покрыты FR-01–FR-13 и NFR-01–NFR-03, критические сценарии и все четыре языковые комбинации успешны. Подтверждены ownership, permissions Content Admin и отсутствие выдачи ключей/snapshot до и после submit. История, прогресс и освоение переживают повторный вход и снятие публикации; изменённый повтор submit отклоняется с 409, а начатая до Draft попытка завершается по своему snapshot.

Пройдены обязательные jobs GitHub Actions, выполнена ручная проверка учебного контента и Admin. Неразрешённые дефекты и ограничения перечислены в отчёте. Публичное размещение требует отдельной задачи и проверки настроек публичного окружения.

Нагрузочные SLO, дополнительная браузерная матрица и автоматический deploy не объявляются критериями, пока они не согласованы. Это не препятствует выполнению описанных функциональных и security-проверок.

## 1. Цели и приоритеты

Проверить основной сценарий подготовки к интервью и наиболее опасные ошибки: доступ к чужим данным, утечку ключей ответов, неверное оценивание, потерю прогресса и рассогласование переводов.

Тесты добавляются вместе с соответствующей функцией, а не отдельной большой задачей после разработки. E2E дополняют более быстрые unit/integration/API-проверки и не заменяют их.

| Приоритет | Риск | Что служит доказательством |
| --- | --- | --- |
| P0 | Пароль или данные одного пользователя доступны другому | DB-проверка хеша, HTTP-проверки двух пользователей и всех защищённых действий |
| P0 | Learner API раскрывает правильные ответы или внутренний snapshot до/после submit | Проверка разрешённых схем payload, вложенных структур, истории и ошибок API |
| P0 | Multiple-choice или порог 80% считаются неверно | Таблицы решений и граничные unit/API-тесты |
| P1 | Результаты теряются, дублируются или меняются после редактирования | Новый вход, повтор отправки, конкурентная отправка, тест снимка |
| P1 | Язык влияет на ID, ответы или прогресс | Все четыре комбинации языков и переключение внутри попытки |
| P1 | Неполная тема опубликована или снятие публикации нарушает доступ/прогресс | Негативные проверки публикации, запрет новых попыток/чтения Draft и сохранность истории/освоения |

## 2. Уровни тестирования

| Уровень | Инструменты и окружение | Что проверяем |
| --- | --- | --- |
| Unit | Python + Pytest, без сети и DB | Single-choice/Multiple-choice, нормализацию наборов, пропуски, порог освоения |
| Integration | Pytest + Django и отдельная PostgreSQL | Уникальность email/переводов/прогресса, транзакции, snapshots, публикацию и выборки владельца |
| API | Pytest + HTTPX, реально поднятый Django и отдельная PostgreSQL | HTTP-статусы, схемы, cookies/CSRF, права, языки, историю и идемпотентность |
| E2E | Playwright + Python + Pytest, реальный frontend/backend/PostgreSQL | Критический пользовательский путь, переключатели, формы, сохранение результата |
| Ручная проверка | Браузер и Django Admin | Полноценность переводов, учебную точность, удобство и администрирование |
| Сборка/конфигурация | Django checks, TypeScript/Vite build, GitHub Actions | Совместимость каркасов, настройки и обязательные jobs |

Возможности для lifecycle Django test DB и интеграции Playwright с Pytest согласуются как служебные зависимости в QIL-002. Их наличие сейчас не предполагается. Отдельный JS-тестовый framework на этапе документации не добавляется.

## 4. Оракулы оценивания

### 4.1. Выбор вариантов

| Тип / ключ | Пользователь выбрал | Ожидание |
| --- | --- | --- |
| Single-choice, `{A}` | `{A}` | Один балл |
| Single-choice, `{A}` | `{B}` или пусто | Ноль |
| Single-choice, `{A}` | `{A, B}` | Невалидный запрос, без результата |
| Multiple-choice, `{A, C}` | `{A, C}` или `{C, A}` | Один балл |
| Multiple-choice, `{A, C}` | `{A}` | Ноль |
| Multiple-choice, `{A, C}` | `{A, B, C}` | Ноль |
| Multiple-choice, `{A, C}` | `{B}` или пусто | Ноль |
| Любой тип | Неизвестный ID, повтор ID или вариант другого вопроса | Невалидный запрос, без результата |

Таблица является оракулом чистого scoring и исторических snapshot, а не разрешением неполного нового HTTP-submit. В QIL-035 отсутствующий вопрос/пустой choice_ids первого in_progress даёт 400 incomplete_answers без submitted; непустой неверный выбор допустим и даёт 0. Генерация ожидаемых баллов не вызывает тестируемую функцию; ожидания независимы и явны.

### 4.2. Освоение

При наличии отметки «Прочитано» проверяем 79/100 — false, 80/100 — true, 81/100 — true. Без отметки все три случая дают false. Дополнительно: 4/5 — true, 3/5 — false, а 199/250 (79,6%) — false, даже если UI округляет процент до целого.

Проверяем `total_count = 0` как невалидное состояние теста. Нельзя допустить деления на ноль или трактовать пустой тест как успешный. При двух неуспешных попытках баллы не объединяются; проверяется успех хотя бы одной самостоятельной попытки.

Порядок действий также параметризуется: сначала тест, потом «Прочитано» и наоборот. Словарь не участвует ни в одном условии.

### 4.3. Auth UI — QIL-018

Frontend unit-тесты проверяют политику регистрации, отсутствие этих ограничений при login, фиксированные маршруты, безопасные русские сообщения и запоздалые ответы восстановления сессии. Публичный словарь распространённых паролей и Unicode-правила сверяются с locked Django/Python командой `python frontend/tools/check_password_policy.py`; 218 примеров проверяются без обращения к DB. Backend остаётся окончательным валидатором.

Playwright запускает production-сборку через Vite preview и реальный Django с отдельной случайной PostgreSQL-базой. Проверяются прямые маршруты, регистрация без auto-login, вход, восстановление после reload, выход/просроченная сессия, duplicate email, already_authenticated, CSRF-отказ, двойной submit, loading/disabled, timeout/network error, неизвестное состояние при сбое `auth/me/`, клавиатура и мобильная ширина. Успешные запросы и серверные отказы проходят настоящий API; только сетевые сбои/потеря CSRF управляются прерыванием запроса. Пароль и cookies не должны попадать в UI/console/Web Storage.

Fixtures закрывают browser contexts, завершают собственные Django/Vite-процессы и удаляют только свою тестовую базу даже при падении. Исходный `test_frontend_smoke.py` сохранён без изменений и работает без DB/backend. Auth E2E не создаёт trace/HAR/video/auth state с секретами. Это покрытие Auth; Learning добавлен отдельно в QIL-019, приёмка всего MVP ещё предстоит.

### 4.4. Learning UI — QIL-019

Unit-тесты покрывают маршруты, RU по умолчанию, язык материала, безопасные цели после login, порядок API, пустой каталог, 403/404/сетевые ошибки, запоздалые ответы и неизвестную отметку при сбое GET. Только явное действие пользователя вызывает `read`; двойной POST блокируется. Потеря ответа требует подтверждающего GET, без автоматического повторения записи.

Playwright использует реальную SPA/Django/изолированную PostgreSQL. `learning_data.py` ограничен случайной базой прогона; создаёт полный RU/EN-контент через существующие модели и test factory. Fixture разрешает менять/удалять только созданные им topic IDs. Проверяются Published/Draft/missing, порядок, статья/словарь RU/EN, reload/Back/Forward, login с переходом на главную, CSRF и автоматическая отметка при видимости конца статьи, общий прогресс RU/EN, отдельное состояние второго пользователя, снятие публикации перед POST, клавиатура и узкий viewport. HTML/JavaScript статьи выводится текстом. Сетевой сбой управляемо прерывается; серверные отказы и данные проходят настоящий API. Quiz/attempts/scoring UI не входят в эту задачу.

### 4.5. Assessment UI — QIL-020

Frontend unit-тесты проверяют radio/checkbox, пропуски, точный payload только из ID, порядок snapshot, независимый язык теста, сохранение выбора и номера вопроса при переводе, GET-восстановление, безопасную проекцию трёх агрегатов и отсутствие клиентского scoring. Покрыты двойные start/submit, 400/403/404/409, поздние ответы и фиксированный payload при неизвестном исходе; автоматических повторов POST нет.

Playwright использует реальный Django/PostgreSQL и существующий изолированный E2E setup. Проверяются четыре пары языка статьи/теста, Back/Forward/reload, оба типа вопросов, CSRF, серверный результат, эквивалентный повтор без второй истории, потеря уже сохранённого ответа submit, явный повтор того же payload, timeout, validation_error, csrf_failed, чужая/отсутствующая попытка, конфликт завершённой попытки, Draft до start и завершение начатой попытки после Draft. Отдельно проверяются потерянный ответ start без автоматического повтора и недоступный GET после 409 без повторной отправки изменённых ответов. Запросы прерываются или портятся только в направленных негативных сценариях; успешные результаты не подменяются.

Тестовый oracle задан factory: Multiple-choice — позиции 10 и 20, Single-choice — 10; ожидаемые агрегаты заданы явно, frontend не импортирует scoring. Fixture удаляет Attempt/TopicProgress только для собственных topic IDs в случайной базе прогона. Вопросы и выбранные ответы не показываются на экране результата; UI не получает правильные ключи или внутренний snapshot. Сохраняются прежние Auth/Learning/smoke; полная приёмка MVP остаётся следующей задачей.

### 4.6. Общий прогресс — QIL-021 / уточнение QIL-027

Прежняя доля mastered Published / все Published — принятый baseline QIL-027. Целевой QIL-034 использует completion-progress: 30% Read, 70% между Published activity, среднее тем; mastery отдельно. Проверяются M=0/пустой каталог, все статусы, лучший результат, отсутствие Practice и изменение весов. Draft исключена из среднего, сохранённые данные не удаляются без reset. In_progress не добавляет вклад и счётчики; история скрыта только в UI, до явного полного reset собственные API/result URL сохраняются.

Loading и 403/404/timeout/network не подменяются нулём. Проверяются очистка приватных значений при истечении сессии, поздние ответы, новый вход, reload и Back/Forward. Sidebar и страница разделяют один запрос прогресса; passive refresh после чтения/submit сохраняет DOM меню и фокус.

### 4.7. Сквозная приёмка — QIL-022

[Матрица QIL-022](MVP_ACCEPTANCE.md) связывает 13 пользовательских шагов с реальными браузерными и API-проверками. `test_mvp_acceptance.py` добавляет четыре полных истории RU/RU, RU/EN, EN/RU, EN/EN: UI-регистрация без auto-login → login/reload → каталог/статья/словарь → чтение → radio/checkbox и смена языка внутри попытки → submit/три агрегата → нормализованный повтор/409 → прогресс/история → logout/новый вход. Эти же истории проверяют desktop/mobile и клавиатуру.

Отдельный сценарий снимает тему с публикации и через `revise_draft` изменяет только публичные тексты собственного Draft-контента, используя существующую транзакционную операцию. Он сверяет прежние публичные RU/EN-проекции вопросов, завершение старой попытки, запрет новых чтения/start и сохранение прогресса. B работает в отдельном browser context; GET прогресса/истории и GET/POST чужой попытки проверяются напрямую через backend. Серверные snapshot и ключи не запрашиваются.

Проверки используют production-сборку, существующий HTTPX/Playwright setup и случайную PostgreSQL-БД; успешные ответы не подменяются. Прежние 54 E2E и smoke сохранены. Публичные ответы проверяются положительными списками полей без дампа данных; пароль/cookies не попадают в console/UI/Web Storage. Допустимые локальные screenshots содержат только синтетический прогресс. Trace/HAR/video/auth state не создаются.

### 4.8. Редакторский сценарий и демо-набор — QIL-024

[Матрица Content Admin](CONTENT_ADMIN_ACCEPTANCE.md) связывает FR-11/FR-12 и QA-12/QA-14/QA-15/QA-16 с реальными формами Django Admin и learner SPA. Content Admin без superuser создаёт все восемь сущностей двуязычного дерева, получает отказ неполной публикации, публикует полную тему, редактирует Published и проверяет `409 edit_conflict`/`400 incomplete_content` без частичного сохранения. Learner видит статью, словарь и оба типа вопросов; живой ключ меняется через Admin, после Draft старая попытка завершается по прежним данным, история/отметка/освоение сохраняются. User/Group/Attempt/TopicProgress недоступны редактору, включая прямые URL и learner ownership.

[Демо-набор и загрузчик](DEMO_CONTENT.md) отделены от технической factory. Шесть PostgreSQL-тестов проверяют явное создание полного Draft, точную идентичность БД, отказ повторной загрузки, сохранность существующих данных, полный rollback и реальную CLI-команду. Seed не запускается автоматически и не содержит аккаунтов или секретов. Существующие HTTPX/TCP, E2E и smoke не ослабляются; временная база и процессы очищаются. Workflow и политика artifacts не меняются. Смысловую эквивалентность и педагогическое качество текста перед публичным использованием подтверждает человек.

### 4.9. Фокус и общая навигация — QIL-026

### 4.11. Сценарий после ручной приёмки — QIL-027

Гость на главной и защищённых маршрутах получает login; после входа открывается каталог на /. Регистрация не создаёт сессию автоматически. Проверяются меню Published-тем, выделение выбранной темы на статье/тесте/результате, mobile раскрытие, keyboard, focus и отсутствие переполнения.

Конец длинной статьи до прокрутки не сохраняет чтение. IntersectionObserver в активной вкладке вызывает один POST с cookie/header CSRF; повторная видимость, reload и RU/EN сохраняют первую дату. Проверяются pending без двойной записи, неизвестное состояние при ошибке GET, настоящий CSRF-отказ, безопасная явная проверка перед повтором, истечение сессии и Published→Draft перед автоматическим POST. Автосохранение не переводит фокус на сообщение. Короткая статья может сохраниться, если целиком видна сразу.

История скрыта только в UI. Сохраняются backend/API-проверки попыток, snapshot, идемпотентности, истории и доступа второго пользователя. Full frontend smoke без backend теперь проверяет безопасное состояние ошибки проверки сессии; полноценный вход и каталог проверяются реальным E2E harness.

## 5. Тестовые данные и изоляция

- Пользователи A и B, отдельный Content Admin в одноимённой Django-группе без superuser и отдельный технический superuser; только синтетические email/пароли. Последний не используется вместо Content Admin в проверках permissions.
- Полная Published-тема с русской и английской статьёй, словарём и пятью вопросами: три Single-choice, два Multiple-choice. Это тестовая фикстура, а не требование к размеру каждого учебного теста.
- Отдельная Draft-тема, у которой по одному удаляются обязательные переводы и поля.
- Независимые выборки для 79/80/81% в unit/API-проверках; не нужно раздувать каждый браузерный тест сотней вопросов.
- Предсказуемые ID и тексты внутри фикстур; переводы соответствуют одним логическим вопросам/вариантам.
- Раздельные cookies и browser contexts для A, B, Content Admin и технического superuser.

Для DB-тестов используется отдельная PostgreSQL/test DB. Для HTTPX нужен отдельный серверный процесс, использующий именно эту тестовую базу: транзакция тестового процесса сама по себе не изолирует записи другого процесса. Согласовать подготовку и очистку фикстур, завершение сервера и защиту от подключения к базе разработки.

API/E2E не очищают пользовательский Docker volume и не используют производственные учётные данные. Параллельный запуск допускается только после изоляции данных каждого worker; на старте последовательный запуск достаточен.

## 6. Особенности API-проверок

HTTPX работает с реально поднятым Django по HTTP. Проверка через mock transport не считается проверкой реального HTTP-контракта. Клиент сохраняет session/CSRF cookies и после login обновляет CSRF-токен.

Нужно проверять статус, тело и отсутствие нежелательных изменений БД: 400 validation_error для структуры и incomplete_answers для неполного первого submit; 403 для session/CSRF; 404 для чужого/Draft/удалённого ID; 409 attempt_already_submitted для изменённого завершённого payload, progress_reset для stale generation и reset_request_conflict для несовместимого повтора UUID. Lookup/порядок отказов и rollback проверяются по новым спецификациям.

Проверки отсутствия утечки до и после submit опираются на формы данных раздела 9 архитектуры и смысл данных. Одного поиска `is_correct` недостаточно: ключ может попасть в JSON под другим именем, вложенным списком или ошибкой. Тестовый Result имеет ровно `correct_count`, `total_count`, `percentage`; метаданные истории проверяются отдельно. Поля тестовых вопросов допустимы только до submit; внутренний snapshot и сохранённые ответы пользователя не возвращаются никогда. Новый PracticeResult содержит только verdict, но expected_answer/его производные/snapshot/submitted_answer запрещены на всех этапах по PQA-16. Bootstrap CSRF и Set-Cookie используются только по назначению и не считаются утечкой.

Для идемпотентности сравниваются ID, payload, результат, `submitted_at` и количество записей до/после повтора. Идентичный нормализованный payload даёт 200, изменённый набор ответов или язык — 409 с кодом `attempt_already_submitted`; проверки порядка ID и пустых ответов соответствуют нормализации в разделе 8.1 архитектуры. При конкуренции одинаковых отправок обе возвращают один результат; при разных payload только одна фиксируется, вторая получает 409. Невалидный payload даёт 400; проверка владельца всегда выполняется раньше выдачи сохранённого результата.

## 7. E2E и ручная приёмка

Основной E2E: регистрация → вход → тема → статья → «Прочитано» → выбор языка теста → оба типа вопросов → отправка → результат → выход → повторный вход → сохранённый прогресс/история.

Четыре комбинации языков проверяются параметризованно; смена языка внутри попытки проверяется отдельно. Дополнительные обязательные сценарии: неуспешный тест, успешная повторная попытка, просмотр словаря без изменения прогресса и отсутствие доступа B к данным A. Для снятой с публикации темы проверяются запрет чтения/новых попыток, сохранение истории/освоения и завершение ранее начатой попытки по snapshot.

Chromium остаётся полным обязательным baseline. QIL-031 согласует дополнительно Firefox/WebKit для критического набора по разделу 4.13; они не считаются PASS без фактического запуска. Проверить основной интерфейс на desktop и узком viewport, клавиатурную навигацию, подписи полей, состояния загрузки и ошибки.

В критических E2E не подменять ответы backend заготовками. Для узкого сценария сетевого сбоя допустимо управляемое прерывание запроса, но оно не заменяет тесты реальной серверной идемпотентности.

Content Admin без superuser вручную оценивает смысл и полноту русских/английских материалов и управляет публикацией. Автоматическая проверка непустого поля не доказывает корректный перевод или учебную точность. Отдельно проверяются запреты административного доступа к User, Attempt и TopicProgress.

QIL-022 подтверждён [run #43428542799](https://github.com/rkcz00/qa-interview-lab/actions/runs/43428542799) для SHA `19bb5eea74ac6870f5a3f32811cdd24280f8de05`. QIL-023 добавляет безопасные JUnit для трёх тестовых jobs без изменения их состава. Все четыре job обязательны на push и pull request в `main`; отсутствующий, skipped, BLOCKED или NOT_RUN job не считается PASS. `continue-on-error` нет; локальный PASS не заменяет CI.

Workflow также поддерживает ручной запуск. Jobs выполняются на GitHub-hosted Ubuntu с правом `contents: read`. Backend и Auth E2E используют раздельные PostgreSQL service containers с временными настройками. Успешный локальный прогон подтверждает проверки в локальной среде. Результат GitHub Actions подтверждается фактическим запуском на GitHub.

GitHub Actions хранит пять компактных JUnit artifacts семь дней: backend, frontend unit и по одному на browser matrix execution Playwright. Четыре job ID дают шесть executions. После реальных тестов общий formatter строит XML только из фиксированного job ID, порядковых case IDs, counts, длительности и статусов. Движок указан в уникальном имени artifact по allowlist matrix. Имена/параметры тестов, exception/SQL/assertion diff, properties и stdout/stderr не переносятся. Raw XML/logs остаются только в `RUNNER_TEMP`; upload ограничен одним новым разрешённым XML-файлом каждого runner с ready-gate, `include-hidden-files: false` и `if-no-files-found: error`. Missing/invalid report не маскируется под PASS.

Formatter/upload выполняются после успеха или ошибки тестов, кроме cancelled; исходный ненулевой exit code сохраняет failure job. Успешный run создаёт только три необходимых XML; build не создаёт artifact. Screenshot/trace/HAR/video/HTML и auth state сейчас не публикуются: безопасная универсальная очистка не реализована. Допустимый fallback на сбое — обезличенный JUnit. Будущий media-upload допускается только после отдельной проверки очистки и с `if: failure()`; сырой trace с session/CSRF запрещён. Подробная политика, результаты аудита и ограничения — в [CI_REPORTS.md](CI_REPORTS.md).

Ошибка обязательного теста должна давать ненулевой exit code и неуспешный job. Публикация JUnit сама по себе не меняет статус job. Автоматические повторы не должны скрывать первоначальное падение; flaky-тест разбирается, а не отключается без объяснения.

## 9. Definition of Done задачи

- Выполнены критерии приёмки конкретной задачи и относящиеся требования PRD.
- Добавлены или обновлены необходимые положительные, негативные и регрессионные проверки по риску.
- Релевантные доступные проверки фактически выполнены; причины `NOT_RUN`/`BLOCKED` указаны.
- Нет известных дефектов, нарушающих безопасность, оценивание или сохранность пользовательских данных.
- Документация отражает фактическое состояние; невыполненные проверки не названы успешными.
- Отчёт содержит результат и ограничения; перехода к следующей задаче без указания пользователя нет.

## 10. Приёмка MVP

Покрыты FR-01–FR-13 и NFR-01–NFR-03, критические сценарии и все четыре языковые комбинации успешны. Подтверждены ownership, permissions Content Admin и отсутствие выдачи ключей/snapshot до и после submit. История, прогресс и освоение переживают повторный вход и снятие публикации; изменённый повтор submit отклоняется с 409, а начатая до Draft попытка завершается по своему snapshot.

Пройдены обязательные jobs GitHub Actions, выполнена ручная проверка учебного контента и Admin. Неразрешённые дефекты и ограничения перечислены в отчёте. Публичное размещение требует отдельной задачи и проверки настроек публичного окружения.

Нагрузочные SLO и автоматический deploy не объявляются критериями, пока они не согласованы. Согласованная дополнительная браузерная матрица QIL-031 описана в разделе 4.13; более широкая OS/device-матрица отдельно не утверждена. Это не препятствует выполнению описанных функциональных и security-проверок.

# PRD — QA Interview Lab

Статус: требования MVP зафиксированы в QIL-001 / Этап B. Реализация приложения ещё не начата. Обновлено: 3 ноября 2026 года.

Связанные документы: [README](../README.md), [архитектура](ARCHITECTURE.md), [QA-стратегия](QA_STRATEGY.md), [backlog](BACKLOG.md).

## 1. Назначение и аудитория

QA Interview Lab помогает Middle/Senior QA Engineers готовиться к техническим собеседованиям на русском и английском языках: читать статьи, изучать термины, проходить тесты и видеть сохранённые результаты.

Дополнительная цель — портфолио, показывающее разработку с Codex и инженерные практики: Python, React, PostgreSQL, Pytest, Playwright, Docker и GitHub Actions. Эта цель не расширяет пользовательские функции MVP.

## 2. Роли и доступ

| Роль | Доступ |
| --- | --- |
| Гость | Регистрация, вход и получение CSRF-токена |
| Пользователь | Опубликованные темы, статьи, словарь, тестирование, только свой прогресс и история |
| Content Admin | Отдельная Django-группа для управления только контентом через Django Admin; permissions определены в FR-12 |

Learner API — пользовательский REST API `/api/v1/`; Django Admin `/admin/` является отдельным интерфейсом. Учебные страницы и Learner API MVP требуют входа. Гостевой просмотр каталога отдельно не реализуется. Роль Content Admin не даёт дополнительных прав в Learner API: доступ к прогрессу и попыткам всегда ограничен владельцем, включая staff и superuser.

## 3. Границы MVP

В MVP входят регистрация по email, вход/выход, каталог тем, одна статья и один набор тестовых вопросов на тему, словарь, два типа вопросов, проверка на backend, история попыток, прогресс и Django Admin.

Вне MVP: подтверждение email, самостоятельное восстановление пароля, практические задания, открытые вопросы, повторение сложных тем. Не планируются дополнительные пользовательские функции вроде социальных входов, рейтинга или поиска. Публичный deploy не входит в QIL-001.

## 4. Словарь продукта

| Термин | Определение |
| --- | --- |
| Topic | Тема подготовки с одной статьёй, набором вопросов и словарём |
| Перевод | Представление той же сущности на `ru` или `en`, а не новая тема или вопрос |
| Draft | Тема редактируется; недоступна в пользовательском каталоге |
| Published | Тема прошла проверки полноты и доступна пользователям |
| Попытка | Работа пользователя с зафиксированным набором вопросов; результат появляется после отправки |
| Прочитано | Явная пользовательская отметка статьи кнопкой, общая для обоих языков |
| Освоено | Есть отметка «Прочитано» и хотя бы одна завершённая попытка с результатом не ниже 80% |

## 5. Основной пользовательский сценарий

1. Пользователь регистрируется с уникальным email и паролем, затем входит.
2. Открывает опубликованную тему и выбирает язык статьи.
3. Читает статью и нажимает «Прочитано».
4. Выбирает язык тестирования независимо от языка статьи и отвечает на вопросы.
5. Отправляет попытку и получает рассчитанный сервером результат.
6. При необходимости повторяет тест. Ранее сохранённые попытки остаются в истории.
7. Выходит и входит снова: отметка, история и статус освоения сохранены.
8. Может изучать словарь; посещение словаря не изменяет освоение темы.

Порядок чтения и тестирования не ограничен: успешный тест до отметки статьи также учитывается после нажатия «Прочитано».

## 6. Функциональные требования и критерии приёмки

### FR-01 — Регистрация по email

- Архитектурное решение: использовать собственную Django User model с уникальным email как идентификатором входа (`USERNAME_FIELD = "email"`). Модель и `AUTH_USER_MODEL` должны быть определены до создания первых миграций и первого запуска `migrate`.
- Обязательны email корректного формата и пароль, проходящий настроенные штатные валидаторы Django.
- Для идентификации email приводится к единой форме: внешние пробелы удаляются, регистр не учитывается. Это явная политика MVP; адреса с разными `+suffix` или точками не объединяются автоматически.
- Уникальность защищена и в API, и ограничением PostgreSQL; две одновременные регистрации одного адреса не создают два аккаунта.
- Пароль передаётся только на создание/проверку и хранится как хеш Django. API не возвращает пароль или хеш.
- После успешной регистрации пользователь может войти без подтверждения email. Автоматический вход после регистрации не требуется.

Приёмка: регистрация валидной пары успешна; повтор адреса, в том числе в другом регистре, отклоняется; невалидный email и пароль отклоняются; сохранённое значение пароля не равно исходному и проверяется средствами Django.

### FR-02 — Вход, сессия и выход

- Вход по email и паролю создаёт Django session. Для неверных данных возвращается общая ошибка без уточнения, существует ли аккаунт.
- Применяется CSRF-защита к изменяющим запросам, включая регистрацию и вход до аутентификации.
- После выхода прежняя сессия не даёт доступа к защищённому API.
- Продолжительность сессии берётся из явно выбранной и документированной настройки Django; отдельного режима «Запомнить меня» нет.

Приёмка: валидный вход даёт доступ к своим данным; неверный пароль и неактивный аккаунт не дают доступ; отсутствие/подмена CSRF-токена блокирует изменяющий запрос; выход прекращает доступ прежней сессии.

### FR-03 — Каталог и статья

- Пользователь видит только Published-темы и может открыть статью на `ru` или `en`.
- Обращение к Draft по известному идентификатору не раскрывает статью или словарь; эти пользовательские запросы отклоняются с `404 Not Found`.
- Открытие страницы или прокрутка статьи сами по себе не отмечают её прочитанной.

Приёмка: опубликованная тема видна и открывается на обоих языках; Draft отсутствует в каталоге и недоступен напрямую; чтение страницы не изменяет прогресс без кнопки.

### FR-04 — Словарь терминов

- У каждой публикуемой темы есть словарь с терминами и определениями на обоих языках.
- В MVP словарь показывается на языке статьи, без третьего независимого переключателя.
- Просмотр словаря не меняет отметку статьи, результат теста или статус освоения.

Приёмка: термины и определения доступны на `ru` и `en`; после посещения только словаря прогресс остаётся прежним.

### FR-05 — Типы вопросов

- Single-choice: один правильный вариант; пользователь выбирает не более одного.
- Multiple-choice: несколько правильных вариантов; пользователь может выбрать несколько.
- В одном тесте допустима смесь типов. Все вопросы имеют одинаковый вес.
- Пропущенный вопрос получает ноль баллов. Тест не может содержать ноль вопросов.

Приёмка: оба типа отображаются и обрабатываются корректно; несколько выбранных вариантов для Single-choice отклоняются backend; отсутствие ответа считается ошибкой, а не исключает вопрос из знаменателя.

### FR-06 — Проверка ответов и результат

- Backend определяет правильность; клиент не может задать балл, владельца или правильные варианты.
- Single-choice даёт один балл за совпадение с единственным правильным вариантом, иначе ноль.
- Multiple-choice даёт один балл только при точном равенстве выбранного и правильного наборов. Порядок выбора не важен. Пропущенный правильный или лишний неправильный вариант дают ноль; частичных баллов нет.
- Неизвестные идентификаторы, варианты другого вопроса и дубли в структуре ответа отклоняются как невалидный запрос без сохранения результата.
- До отправки попытки клиент получает только явно разрешённые публичные поля: идентификаторы, порядок, типы и тексты вопросов, а также идентификаторы, порядок и тексты вариантов на выбранном языке.
- Learner API никогда не возвращает правильные ответы и внутренний snapshot (`content_snapshot`) — ни до, ни после submit, включая историю, ошибки и вложенные данные. Редактирование ключей разрешено только в защищённом Django Admin при наличии контентных permissions.
- После submit объект результата содержит только агрегированные `correct_count`, `total_count`, `percentage`. По-вопросные оценки, вопросы, варианты и выбранные ответы завершённой попытки не выдаются. ID попытки, тема, язык и дата остаются отдельными метаданными истории; это не расширяет состав результата. Формы ответов определены в [API-контракте](ARCHITECTURE.md).

Приёмка: для Multiple-choice с ключом `{A, C}` наборы `{A, C}` и `{C, A}` дают один балл, `{A}`, `{A, B, C}`, `{B}` и пустой набор — ноль. Ответы Learner API не содержат ключей правильности или внутреннего snapshot ни до, ни после submit; результат содержит только три согласованных агрегата. Подставленные клиентом баллы не принимаются.

### FR-07 — Отметка «Прочитано»

- Только явное нажатие кнопки сохраняет отметку для пары пользователь/тема.
- Повторное нажатие не создаёт дубликаты. Отметка одна для обоих языков.
- Сброс отметки пользователем не входит в MVP.

Приёмка: отметка переживает перезагрузку страницы, смену языка и новый вход; нажатие одним пользователем не влияет на другого.

### FR-08 — Освоение темы

Тема освоена тогда и только тогда, когда статья отмечена прочитанной и существует хотя бы одна завершённая попытка с результатом не ниже 80%.

Проверка порога: `100 * correct_count >= 80 * total_count`, где `total_count > 0`. Округление процента для отображения не участвует в решении.

Приёмка:

- «Прочитано» без успешной попытки — не освоено.
- Успешная попытка без «Прочитано» — не освоено.
- «Прочитано» и 4/5 (80%) — освоено; 3/5 (60%) — не освоено.
- 79/100 — не освоено; 80/100 и 81/100 — освоено при наличии отметки.
- Две неуспешные попытки не суммируются в успешную.
- Более поздний низкий результат не отменяет уже выполненное условие.
- Словарь, смена языка и повторный вход не сбрасывают освоение.

### FR-09 — Повторные попытки и история

- Пользователь может начать новую попытку только для Published-темы; завершённые попытки сохраняются независимо друг от друга. Для Draft создание новой попытки отклоняется с `404 Not Found`, даже по ранее известному ID темы.
- При начале попытки, до выдачи вопросов клиенту, backend создаёт неизменяемый снимок: идентификаторы и порядок вопросов, их типы, варианты с идентификаторами и порядком, правильные ответы для серверной проверки и необходимые русские и английские тексты темы, вопросов и вариантов.
- История показывает тему, язык при отправке, время и результат каждой завершённой попытки.
- Начатая, но не отправленная попытка не имеет результата и не влияет на освоение.
- Повтор submit с тем же `attempt_id` и тем же payload после нормализации возвращает прежний результат с `200 OK`, без второй записи истории и изменения времени отправки. Изменённый payload завершённой попытки отклоняется с `409 Conflict`, без перезаписи результата. Нормализация и ошибки определены в API-контракте.
- Последующее редактирование контента и сам переход Published → Draft не пересчитывают историю, прогресс, сохранённые оценки или освоение. Эти данные сохраняются и доступны владельцу; статус публикации не участвует в условии освоения.
- Последующее редактирование темы, изменение или переупорядочивание вопросов и вариантов либо снятие темы с публикации не препятствуют отправке уже начатой попытки. Её результат определяется только по снимку начала попытки, а не по актуальному состоянию вопросов; языковое переключение использует тексты и идентификаторы того же снимка.

Приёмка: после двух завершённых попыток в истории две записи; повтор идентичного submit возвращает тот же результат и не создаёт третью; изменённый payload даёт 409 без изменения данных. Редактирование и снятие публикации не меняют старые числа, snapshot, прогресс и освоение; новые попытки для Draft запрещены, история доступна после нового входа. Завершение ранее начатой попытки добавляет её результат и обновляет прогресс по прежним правилам FR-08.

Дополнительная проверка: начать попытку, затем изменить порядок, варианты, ключи ответов и переводы исходных вопросов и снять тему с публикации. При переключении языка и отправке используются исходный снимок и его порядок; результат соответствует исходным ключам, а не отредактированным вопросам.

### FR-10 — Независимость языков

- Поддерживаются `ru` и `en`; язык статьи и язык тестирования выбираются отдельно.
- Для каждой из комбинаций `ru/ru`, `ru/en`, `en/ru`, `en/en` доступны соответствующие тексты и одни и те же логические сущности.
- Переключение языка не меняет `topic_id`, `question_id`, `choice_id`, набор вопросов или уже выбранные варианты текущей попытки.
- Переключение само по себе не создаёт попытку, результат или запись прогресса.
- Сохранённый прогресс привязан к пользователю и теме, без измерения «язык».

Приёмка: при смене языка до отправки сохранены ответы по ID и номер текущего вопроса; после смены языка статьи язык теста не изменён; история, отметка и освоение прежние. Сохранение самих языковых предпочтений между устройствами отдельно не требуется.

### FR-11 — Полнота и публикация

Тема создаётся в Draft. Для перехода в Published обязательны:

- Непустые название и статья на `ru` и `en`.
- Хотя бы один вопрос и не менее двух вариантов у каждого вопроса.
- Тексты каждого вопроса и каждого варианта на `ru` и `en`.
- Ровно один правильный вариант у Single-choice; не менее двух у Multiple-choice.
- Хотя бы один термин словаря с названием и определением на `ru` и `en`.
- Содержательно полноценные и эквивалентные переводы, проверенные администратором.

Backend проверяет наличие и структуру данных; качество и смысл переводов оценивает человек. Автоматический перевод или автоматическая оценка его качества не входят в MVP.

Приёмка: отсутствие любого обязательного перевода, пустые или пробельные тексты либо невалидная структура ответов блокируют публикацию с указанием ошибки. Неполная тема остаётся в Draft. Published-тему можно редактировать, пока итоговый контент полностью соответствует тем же требованиям. При нарушении полноты изменение откатывается целиком.

### FR-12 — Django Admin

- Content Admin — отдельная Django-группа с permissions `view/add/change/delete` только для `Topic`, `Question`, `Choice`, `Term` и их переводов. Статья является частью перевода Topic; отдельная роль редактора не вводится.
- У группы нет permissions для `User`, `Attempt`, `TopicProgress` или управления группами/permissions. Учётная запись Content Admin имеет `is_staff=True`, `is_superuser=False`; superuser не является моделью обычного Content Admin. Точный перечень моделей и границы доступа определены в архитектуре.
- Публикация выполняется через общую серверную проверку; операция массового изменения статуса не обходит её.
- Обычный пользователь не может управлять контентом через Admin или пользовательский API.
- Тема с историей попыток не удаляется физически через Admin; для снятия с каталога используется Draft.

Приёмка: Content Admin без superuser может подготовить и опубликовать полноценную тему; неполная не публикуется. Списки, отдельные записи и действия над User, Attempt и TopicProgress недоступны этой роли в Admin, включая прямой URL. Обычный аккаунт не получает доступ к редактированию; история сохраняется при снятии темы с публикации.

### FR-13 — Изоляция пользовательских данных

- Прогресс и попытки принадлежат аутентифицированному пользователю. Переданный клиентом идентификатор владельца не принимается.
- Ограничения действуют для списков, отдельных объектов, начала/отправки попытки и отметки статьи.
- Пользователь B не может прочитать или изменить данные A по известному идентификатору.
- Скрытые в Draft статья и словарь недоступны пользователям. Собственные история и прогресс остаются доступны без актуального Draft-контента и без внутреннего snapshot. Уже начатую попытку можно завершить по сохранённому серверному snapshot согласно FR-09; до её submit доступны только разрешённые поля вопросов.

Приёмка: прямые HTTP-запросы B к попытке A не раскрывают данные и не меняют их; списки B не содержат записи A; подмена владельца отклоняется; после выхода защищённые запросы не выполняются.

## 7. Нефункциональные требования

### NFR-01 — Защита данных

Пароли и их хеши не возвращаются пользовательским API. Штатная передача session cookie браузеру через `Set-Cookie` и выдача CSRF-токена собственному клиенту по назначению разрешены. Пароли, их хеши, сессионные секреты и CSRF-токены не должны попадать в Git, логи, отчёты или диагностические артефакты. Утечки сессионных секретов и CSRF-токенов в непредназначенные для них API-ответы запрещены.

Для публичного окружения обязательны HTTPS, безопасные настройки cookie и отключённый debug; это проверяется перед согласованным публичным запуском. Статьи и термины отображаются как текст без исполнения внесённого HTML/JavaScript.

### NFR-02 — Воспроизводимость и проверяемость

Согласованный стек: React + TypeScript + Vite; Python + Django + DRF; PostgreSQL; Django Admin; Pytest + HTTPX; Playwright + Python + Pytest; Docker + Docker Compose; GitHub Actions. Приложение и DB-проверки используют PostgreSQL. Минимальный request/response, HTTP-статусы, CSRF и ownership обязательны по разделу 9 [архитектуры](ARCHITECTURE.md); обязательные CI jobs определены в разделе 8 [QA-стратегии](QA_STRATEGY.md). Версии и команды запуска фиксируются по мере реализации. Провал обязательной проверки делает CI неуспешным; диагностические артефакты не содержат реальных пользовательских данных и секретов.

### NFR-03 — Понятное взаимодействие

Пользователь видит ошибки форм и запросов, тип вопроса, результат и статус прогресса. Основные формы, кнопки и варианты доступны с клавиатуры и имеют понятные подписи. Сетевой сбой отправки не должен показывать выдуманный результат или терять уже сохранённую попытку.

## 8. Критерий готовности MVP

FR-01–FR-13 и NFR-01–NFR-03 реализованы и проверены по QA-стратегии. На тестовых данных воспроизводится основной сценарий, все четыре языковые комбинации и изоляция двух пользователей. Создана минимум одна полноценная демонстрационная тема; точный учебный материал согласуется отдельно. Обязательные CI jobs успешны; непройденные проверки и оставшиеся ограничения явно описаны.

Статус QIL-001 относится только к документации и не является приёмкой MVP.

## 9. Принятые технические уточнения

- Равный вес вопросов, ноль за пропуск и отсутствие частичных баллов дают однозначную оценку.
- Освоение определяется по любой успешной завершённой попытке; худший последующий результат, редактура контента и снятие темы с публикации автоматически его не отменяют.
- Словарь следует языку статьи. Отдельная настройка языка словаря не добавляется.
- Снимок попытки обеспечивает стабильный результат и работу переключателя языка при редактировании исходного контента.
- Таймер, случайная выборка вопросов, возобновление незавершённого теста как отдельный пользовательский сценарий и отдельный интерфейс управления пользователями не добавляются.

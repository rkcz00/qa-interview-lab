# Practice UI — QIL-030

Источник поведения — [PRACTICE_SPEC](PRACTICE_SPEC.md). Backend/API, миграции, зависимости и правило mastery не меняются. Интерфейс продолжает существующие русский UI, AppShell, tokens, Sidebar, Button/Notice и независимые языки.

## Маршруты и API

- `/topics/{topic_id}/practice` — preview и только явный start; `/practice-submissions/{submission_id}` — собственная работа либо сохранённый verdict.
- Query принимает только один language=ru|en, по умолчанию ru. Вход со статьи/результата теста использует язык материала, а не язык теста. Прямые URL и SPA fallback, Back/Forward и active-навигация сохранены.
- Ссылка на тему/результате теста появляется только после успешного preview. Отсутствие конфигурации, Draft Task/Topic и missing resource дают 404 и скрывают вход. Перед Read/любым submitted-тестом preview показывает причины, start disabled. Backend остаётся источником допуска.
- Новая группа API-клиента practice: preview/start/get/submit/delete поверх прежнего GET/POST wrapper. Никаких дополнительных fetch, внешних API или выполнения кода. POST содержит только согласованные поля, credentials include и свежий CSRF; delete — POST с {} и 204.
- Public DTO и runtime decoders строго ограничивают поля, статусы, kind, RU/EN, режимы нормализации, verdict и лимит. expected_answer/его производные, внутренний snapshot, source_revision и сохранённый ответ не принимаются и не отображаются.

## Ответ, результат и удаление

Условие, общий код, входные данные, окружение и формат вывода отображаются как экранированный текст. Textarea сохраняет исходную строку только в памяти и при смене языка; счётчик считает code points. HTML maxlength не используется, поскольку он считает UTF-16 units. Пустая строка не блокирует submit: допустимость определяет сервер. NUL/surrogates и превышение 5000 отмечаются до отправки; нормализация остаётся только серверной.

Выполняющийся submit блокирует редактирование и повторное нажатие. Подтверждённые 400/CSRF сохраняют ввод для явного исправления; ошибки поля фокусируют textarea, остальные — безопасное сообщение. При network/timeout фиксируется неизменяемый payload и выполняется GET. Новый POST возможен только явно с тем же payload после in_progress; при неизвестном GET повтор запрещён. 409 загружает сохранённый результат и не разрешает изменённый повтор. После результата остаются только публичный контекст и Верно/Неверно, текст ответа удаляется из состояния.

По замечаниям ручного просмотра строка «Неверно» использует красную палитру Notice error, «Верно» — зелёную success. Сохранённый ответ, эталон и snapshot в результат не добавляются.

Основное действие завершённой работы — «Пройти заново». Оно вызывает существующий POST start темы на submitted_language и открывает новый submission ID с пустым полем ответа. Предыдущая работа и её результат сохраняются; DELETE/POST delete для этого действия не вызываются. Back возвращает к прежнему результату. Двойное нажатие блокируется; запоздалый ответ после ухода игнорируется. При отказе нового start прежний результат остаётся виден; после 403/404 доступ к новому запуску проверяется повторно при перезагрузке. Неизвестный исход start показывает предупреждение: автоматического повтора нет, явный новый запуск может создать ещё одну работу. Это отличается от повтора того же submit с зафиксированным payload.

Удаление сохранённого результата доступно отдельной кнопкой «Удалить результат» и требует подтверждения с доступным фокусом и отменой. Незавершённую работу по-прежнему можно удалить до отправки. Неопределённое удаление проверяется GET: 404 подтверждает отсутствие; существующая работа разрешает только явный повтор. После успешного удаления выполняется preview GET и переход к практике темы либо к каталогу, если она недоступна. Потеря сессии/404 очищает локальный ответ; чужие ID не раскрываются.

Уход с несохранённым ответом предупреждает перед SPA-ссылкой, Back/Forward, logout и browser reload/закрытием. Перед обработкой popstate роутер синхронно отправляет отменяемое внутреннее событие; при отказе возвращается URL работы, React-экран не снимается. Смена языка в пределах того же URL не считается уходом и сохраняет ввод/фокус. Reload восстанавливает только условие и статус; неотправленный текст не сохраняется. localStorage/sessionStorage, autosave, история практики и новые счётчики отсутствуют. Практика не вызывает обновления mastery и не изменяет общий процент.

## Проверки и текущие ограничения

Добавлены frontend unit/type-contract проверки и реальные Playwright-сценарии: статья → тест → практика, prerequisite/404, RU/EN, фокус, keyboard, 1280×900 и 390×844, reload, пустой ответ, correct/incorrect, повторы/409, network uncertainty, удаление, ownership, snapshot после unpublish и отказ небезопасного ответа API. Только негативный decoder-сценарий изменяет ответ реального API; успешные запросы проходят настоящий backend/PostgreSQL.

Seed [practice_data.py](../tests/e2e/practice_data.py) вызывается только E2E fixture и отвергает dev-БД. Все изменения/cleanup ограничены Topic IDs, созданными fixture в случайной временной БД. Демо-практика в dev-БД автоматически не создаётся. Сырые ответы, credentials, screenshots/trace/video/auth state и DB dumps не сохраняются. Общая политика — [CI_REPORTS](CI_REPORTS.md).

Полный ручной прогон пользователя от 20 ноября — PASS: npm ci по прежнему lock, миграции временной PostgreSQL, Django checks, makemigrations/migrate --check, pip check, 332 backend/HTTPX-теста и 22 подтеста, 198 frontend unit, type-check/build и 96 Playwright. TEMP_CLEANUP, FILES и итоговый RESULT — PASS. Файлы совпадают с версией, переданной на прогон; финальные изменения после лога ограничены статусами документации.

Регрессионная защита несохранённого ответа проверяет отмену Back до смены React-состояния. E2E явно ожидает диалог и восстановленный URL; два unit-кейса покрывают отмену/разрешение перехода, смену языка и cleanup обработчика. Этот сценарий входит в успешный полный реальный Playwright-прогон.

В Codex отдельно прошли 198 frontend unit, type-check/build, Markdown/ссылки, Python syntax, diff --check и проверка секретов. Предварительная браузерная диагностика с синтетическим API не подменяет реальные E2E. PostgreSQL/Docker-доступ Codex ранее BLOCKED политикой и не повторяется; доказательство полной локальной интеграции — предоставленный ручной лог. Локальная приёмка QIL-030 — PASS. Результат всех четырёх GitHub Actions jobs проверяется после публикации для точного SHA и фиксируется в итоговом отчёте задачи.

## Один ручной запуск

Правки после ручного просмотра отдельно проверены Codex: 211 frontend unit, type-check/build и 16 Playwright (все Practice UI и smoke) — PASS. Новые сценарии покрывают оба verdict, RU/EN, desktop/mobile, один start при повторном нажатии, пустой новый ответ, сохранность прежнего результата и прогресса, unpublish и потерянный ответ нового start. Пользователь одобрил правки. Проверки используют временную PostgreSQL с cleanup; dev-БД не используется. Backend/API, миграции и зависимости не менялись. Полный backend regression и вся папка E2E на этапе локальной проверки не запускались. На том этапе commit/push не выполнялись; итог CI точного SHA фиксируется отдельно в отчёте публикации. Результаты исходного полного прогона выше относятся к базовой реализации.

Из корня проекта:

```powershell
.\.venv\Scripts\python.exe .\tools\check_practice_ui.py
```

Либо запустите tools/check_practice_ui.py системным Python по абсолютному пути из любой папки. Он выполняет npm.cmd ci по существующему lock (кэш только frontend/.cache), сверяет сохранность файлов и запускает прежний [изолированный QA runner](PRACTICE_BACKEND.md#один-файл-проверки) через проектную .venv. Тот проверяет миграции на временной PostgreSQL, backend/HTTPX, Django/pip, frontend unit/type-check/build и всю текущую папку Playwright; очищает принадлежащие прогону БД/процессы.

Критерий: NPM_CI=PASS, все последующие стадии PASS, TEMP_CLEANUP=PASS, FILES=PASS и RESULT=PASS. Ошибки/NOT_RUN/BLOCKED не считаются успешной приёмкой. Установка глобальных пакетов/браузеров, изменение ExecutionPolicy/PATH, вызовы Docker API и очистка volumes этим скриптом не выполняются. При native EPERM необходимо освободить файл, а не менять политику PowerShell.
